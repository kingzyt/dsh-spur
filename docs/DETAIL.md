# 会话保活提醒

右侧工具区里的一个按会话开关的定时提醒器（包名 `@kingzyt/dsh-spur`，内部标识 `spur`）。开关默认关闭，由用户手动打开；打开之后，会话每个正常结束的回合都会在间隔之后收到一条提醒。提醒只讲两条内容，不解释插件机制，也不往系统提示词里写任何东西。

提醒是这样进来的：到点之后调用 `agent.followup()`，在智能体空闲时开一个新回合，消息的 `source` 是 `{ kind: 'spur', form: 'notice', summary }`，界面上显示为一条可折叠的提示行（折叠时只有一句摘要，展开是模型看到的那段话）。

## 提醒的内容

```
【保活提醒】你停下来了，「全部任务」确定完成了吗？

1. 没完成就继续做，不要偷懒，也不要停下来等确认。
2. 上下文到 60% 以上才需要担心预算：先用 context_usage 查真实占用。60% 以前不用焦虑，上下文够用；流程要求压缩时（例如开始新的一步、切换任务）照流程用 compact_context 压，不受这个百分比限制。
```

第 2 条按工具注册表动态出现：`context_usage` 与 `compact_context` 都在才同时提两个工具名；只有查询工具就只说查询；都没有就只说「60% 以上才需要担心预算」。60% 这个数就是面板里的「压缩底线」，可以改。它只是预算焦虑的门槛，不是压缩许可：流程（`/multi-step-plan` 每步开工）要求压缩时，提醒明确写着不受百分比限制。

除此之外没有任何说明：不提 `spur_reply`，不提回合、计时器、系统提示词这些机制。

## 开关与停止

- **开关默认关闭**：右侧面板里每个会话各一个开关，开不开由用户决定；关着的会话一条提醒都不会收到。
- 打开之后，每个正常结束的回合都在间隔之后提醒一次，没有次数上限。
- **主智能体声明停用**：调用 `spur_reply`，`reply` 参数填「已经完成所有任务」（做完）、「进行不下去」（确实卡住做不了）或「暂停」（等你回来再继续），末尾的句号、空白会被忽略——本会话的提醒关闭，用户之后再说新话也不会自动恢复，只能在面板里手动重新打开。重新打开会同时清掉这个标签。
- **用户手动关掉**：面板开关关掉，效果相同，直到重新打开。

`spur_reply` 的说明只讲怎么填，不讲机制：填三个停用标签之一就关，填别的就继续。借鉴内置 goal 的 phase 思路——任务结束可能是「完成」、可能是「确实做不下去」、也可能是「等你回来」，三种都不该让定时器继续空转。

## 不打扰的情况

- **子代理还在跑**：到点时先不提醒，隔一个间隔再看；等这棵会话树里所有子代理都空闲了，才提醒主会话。判断走会话头的 `parentSession` 链，只看仍然在进程里的子代理。
- 会话里存在当前目标（goal）不构成跳过理由：开关是用户的决定，目标续轮与保活提醒可以并存；
- 子智能体会话本身（`origin === 'subagent'` 或 `delegationDepth > 0`）：它自己不会收到提醒，提醒由父会话负责；
- 回合是用户按停止、出错、被中止结束的：只有 `reason.kind === 'completed'` 的回合才进入判断；
- 会话正在跑：计时只在回合结束时排，到点那一刻还在跑就跳过，等这个回合结束再重排；
- 排定的那一刻，会话已经不在、收件箱里有别人排着的消息：这一次就放弃。

面板上的「立即提醒一次」同样要求会话已启用且空闲：运行中会被拒绝，按钮也是禁用的。面板显示的运行状态取自会话快照，是实时的。

## 右侧工具区的配置面板

插件注册了一个右侧栏页签（类型 `spur`），入口在右侧工具区的「指南」页里，点「保活提醒」打开；打开后它作为当前会话的页签留在那里。面板内容：

1. **本会话开关**：默认关闭。
2. **状态**：运行中 / 空闲 / 未加载，是否已排定提醒；主智能体声明停用后显示是「全部完成」「进行不下去」还是「暂停」。
3. **立即提醒一次**：会话已启用且空闲时才能按。
4. **发给 AI 的提醒**：面板里直接显示这条消息的原文；改参数或翻开关时立即跟着变，约半秒后自动保存并对后续提醒生效。
5. **提醒记录**：本会话的探查次数（定时检测了多少次，包含到点但没发提醒的那些）、提醒次数，以及最近三次提醒的时间。这些记录挂在会话 id 上并写入 profile 目录，刷新页面、插件重载都不会丢；DSH 重启后仍从记录文件恢复。
6. **全局参数**：预算焦虑门槛（`compactFloorPercent`）、连续几次提醒没动静就主动压缩（`compactAfterIdleNudges`，0 表示不做）、两条提醒之间至少隔几分钟（`idleGapMinutes`，默认 2）、开启后的反悔期秒数（`enableGraceSeconds`，默认 30）、「任务结束后自动关机」开关、「自动任务模式」开关与那段可编辑的追加提示词（`autoTaskHint`）。改动自动保存并立即生效，不重启、不重载插件；底部只有「恢复默认」。

数据都落在 profile 目录的 `spur/` 下（路径由宿主服务 `ctx.get('profileContext').dir` 提供，进程环境里没有 `DSH_PROFILE_DIR` 也能定位）：`settings.json` 存面板保存的全局参数，`records.json` 存按会话 id 记的开关、停用标签、探查/提醒次数与最近三次提醒时间。两者都不是 profile 的 `cordis.patch.yml`，所以面板保存过的值优先于行配置与代码默认值。面板与宿主半边通过 `GET /api/spur.state` 与 `POST /api/spur.action` 两条路由通信；没保存的草稿留在浏览器的 `localStorage`，切页签或刷新页面后仍在（预览会标明它是未保存草稿）。

## 空闲就提醒（事件驱动 + 兜底巡检）

主智能体每次从运行中回到空闲，插件在收到 `agent/status`（`status: 'idle'`）的那一拍发提醒，像内置目标那样逐轮驱动。

- 只有正常结束的回合才算数：`turn/end` 的 `reason.kind` 是 `completed` 才置位，被中止或报错的回合不戳。
- 会话在忙、子代理在跑、收件箱里有别人的消息时让路。
- 同一会话两条提醒之间至少隔 `idleGapMinutes`（默认 2 分钟），防止「回合瞬间结束」把提醒打成一串。
- 兜底巡检：每 `watchdogSeconds`（默认 60 秒，不在面板里）扫一遍被监视的会话，凡是开着、空闲、没有待办计时器的就补一次检查。它兜住的是事件丢失、插件重载、会话在面板打开前就停着这几类静默。

## 连续没动静就自动压缩

参数 `compactAfterIdleNudges`（默认 3，0 表示不做）：连续 N 次提醒之间一次工具动作都没发生，就认为会话被上下文压住了，叫也叫不动。

到第 N+1 次该提醒时，插件先调宿主的压缩服务把会话压一次（`compactNow`：把此前可压缩历史收成一条摘要检查点），再在干净上下文里发那条提醒。计数在出现任何 `tool/result` 或用户说话时清零，所以正常推进的会话不会被压。

宿主层没有压缩服务时只写一条警告日志，然后照常提醒，不会卡死。本机的压缩后端由 `@local/dsh-context-tools` 这个包提供（它就是靠和这里同一份 `ctx.compaction` 工作的）。

## 任务结束后自动关机

默认关闭。打开之后，主智能体用任意一个停用标签（完成 / 进行不下去 / 暂停）结束任务时，插件会在一个提醒间隔之后再检查一次：那时开关还开着、停用标签还在，就执行关机命令。

- Windows 上执行 `shutdown /s /t <shutdownGraceSeconds>`（默认 60 秒）；这期间面板上出现倒计时和「撤销关机」按钮，点一下执行 `shutdown /a`，也可以直接在命令行里 `shutdown /a`；
- 一个停用标签只触发一次；在检查之前重新打开开关会取消还没到点的检查；关机已经发起但还在宽限期里时，重新打开开关也会顺手撤销；
- 只在 Windows 上实现，其他平台只写一条警告日志；
- `shutdownDryRun` 打开时只记日志、不执行，撤销也走干跑，用来试开关或跑冒烟。

面板里会显示「已排定关机：约 N 分钟后检查一次」；发起之后显示倒计时和「撤销关机」，宽限期过后只剩「已发起关机」的说明。

## 配置

一般来说不用碰配置文件，直接在右侧面板里改。没有面板的场合（例如 headless 启动）可以在 profile 的 `cordis.patch.yml` 里按 id `spur` 覆盖，只写要改的字段：

```yaml
- id: spur
  name: '@kingzyt/dsh-spur'
  config:
    idleGapMinutes: 2
```

| 字段 | 默认 | 作用 |
|---|---|---|
| `compactFloorPercent` | `60` | 提醒里写的预算焦虑门槛百分比，不是压缩许可 |
| `shutdownOnHalt` | `false` | 主智能体声明停用后，下一次检查时若还停着就关机 |
| `shutdownGraceSeconds` | `60` | 关机命令的宽限秒数（`shutdown /s /t`） |
| `shutdownDryRun` | `false` | 只记日志不执行关机，用来试开关 |
| `autoTaskMode` | `false` | 打开后每条提醒末尾追加 `autoTaskHint` 的正文 |
| `autoTaskHint` | 内置五条要求 | 追加的提示词正文，面板里可改，「恢复默认」回到内置文本 |
| `compactAfterIdleNudges` | `3` | 连续几次提醒没有工具动作就主动压缩一次；`0` 表示不压缩 |
| `enableGraceSeconds` | `30` | 打开会话开关后的反悔期，这段时间不发提醒 |
| `idleGapMinutes` | `2` | 两条提醒之间至少隔多少分钟 |
| `watchdogSeconds` | `60` | 兜底巡检周期；事件丢了也能补一次检查 |

## 限制

- 插件在进程里计时，但开关、停用标签与提醒记录会写进 profile 目录的 `records.json`：刷新页面、插件重载、DSH 重启后都能恢复；DSH 重启期间没发出去的提醒不会补发。
- 判断不读回复文本，也不看这一回合做没做工具：只要开关打开、又没有完成标签，每个正常结束的回合都会提醒——这正是这套设计的规则，插件不猜。
- 提醒本身是一次普通的模型回合，会正常消耗 token；不设次数上限，要停就关开关或让主智能体填完成标签。
- 子智能体会话不在范围内。
- 面板只在 Web 界面里有；没有 `connection` 服务的部署（headless）只有 `spur_reply` 与提醒逻辑，没有路由与页签（也就打不开开关，默认不会提醒）。
